# 言い換えの判定基準と、実例集

実例はすべて、**実際に公開した記事から拾ったもの**です。同じ書き手の記事の中に、良い例と悪い例の両方があります。

## 判定の基準

**その用語が「何をするものか」が書かれているか。** これだけです。

| | 説明になっている | なっていない |
|---|---|---|
| 略語 | **機能で言い換える** | アルファベットを伸ばす |
| カタカナ語 | **機能で言い換える** | 別のカタカナに置き換える |
| 業界語 | **読者の業務の言葉に置き換える** | 定義文を貼る |

## ✅ 良い例（実記事より）

| 用語 | 書き方 | なぜ良いか |
|---|---|---|
| LLM | `LLM（パソコンの中だけで動くAI）` | **どこで動くか**が分かる。読者の関心（社外に出るのか）に答えている |
| Claude | `Claude（クラウド上のAI）` | 上と対になっていて、違いが分かる |
| TUI | `TUI（画面の枠やロゴ）` | **目に見えるもの**で説明している |
| PMP | `PMP（プロジェクトマネジメントの国際資格）` | 何の資格かが分かる |
| GAS | 「**Googleの無料プログラム**」 | 誰の・いくらの・何か、が1行で分かる |

## ⚠️ 展開しただけの例（実記事より・要改善）

| 用語 | 書き方 | 何が足りないか |
|---|---|---|
| GAS | `GAS（Google Apps Script）` | **伸ばしただけ。** 読者は「Apps Script」も知らない |
| Substack | `Substack（サブスタック）` | **カタカナにしただけ。** 何ができる場所か不明 |
| Obsidian | `Obsidian（私のメモアプリ）` | 惜しい。「私の」が主語で、読者には関係がない |

> **同じ書き手でも、記事によってぶれます。** だから点検が要ります。

## よく出る用語と、言い換えの方向

そのまま貼らず、**原稿の文脈に合わせて**書き換えてください。

| 用語 | 方向 |
|---|---|
| API | 「システム同士をつなぐ窓口」「別のソフトから操作するための入口」 |
| RAG | 「社内の資料を検索して、その内容をもとにAIが答える仕組み」 |
| リードタイム | 「受けてから終わるまでの時間」 |
| 属人化 | 「その人しか分からない状態」 |
| KPI | 「目標に近づいているかを見る数字」 |
| 一次解決率 | 「最初のやり取りだけで片づいた割合」 |
| 直行率 | 「手戻りなく一度で通った割合」 |
| MTTR | 「止まってから直るまでの平均時間」 |
| オンプレ | 「自社の中に置いたサーバー」 |
| デプロイ | 「作ったものを本番で動く状態にすること」 |
| リポジトリ | 「プログラムの保管場所」 |
| フロントマター | 「ファイルの先頭に書く設定部分」 |
| symlink | 「本体は1か所に置いて、別の場所からたどれるようにする仕組み」 |

## 実記事10本で分かった、拾い漏れやすい語

公開済み記事10本（事業者向け5・開発者向け3・一般向け2）にかけた結果です。

**① 定型文の中の用語は、全記事で同じ穴になる**

`要件定義` は、事業者向け4記事**すべて**で未説明でした。フッターの定型文に入っていたためです。
**毎回コピーする文の中の用語は、一度も点検されないまま増えます。**

**② 書き手が作った言葉は、いちばん見落とされる**

開発者向けの記事で指摘された15語のうち、大半が**その記事の中で書き手が作った言い回し**でした。

`発火する` / `実体` / `ピア` / `一覧の鮮度` / `固有トークン` / `公式パス` / `プローブ用スキル`

一方で `Git` `CLI` `JSON` `YAML` `非TTY` `サブコマンド` は正しく「説明不要」と判定されています。
**標準的な用語より、自作の言い回しのほうが危ない。**

**③ 同じ語でも、記事によって判定は変わってよい**

`属人化` は、ある記事では ✅（直前に説明あり）、別の記事では ⚠️ でした。
**語ではなく、その原稿での扱われ方を見ます。** 一覧表の暗記ではありません。

## 医療・法律・金融の用語（慎重に）

平易にすることと、言い切ることは別です。

| 用語 | 言い換えの方向 | 注意 |
|---|---|---|
| ASD | 「対人関係やこだわり、感覚の受け取り方に特性が出やすい発達障害のひとつ」 | **診断の説明にしない。**「〜と説明されることが多い」の形に |
| 療育 | 「生活しやすくなる力を、専門家と練習する支援」 | 効果を断定しない |
| クールダウン | 「気持ちが高ぶったときに落ち着くための行動」 | 方法を処方しない |
| 青色申告 | 「帳簿をきちんとつける代わりに、税の優遇が受けられる申告のしかた」 | **要件・金額を断定しない。**「詳しくは税務署や税理士に」を添える |

**用語を噛み砕いた結果、書き手が踏み込みすぎるのが一番危ないパターンです。**

## 業務資料でいちばん詰まるもの（技術用語ではありません）

引き継ぎ資料・手順書・マニュアルを点検するときは、**ここを重点的に見ます。**

### ① 社内の略語・業界特有の言い方

その職場・その業界では日常語なので、**書き手は用語だと認識していません。**

- 業界の中でだけ通じる呼び方（外から来た人には、何を指すのか見当もつかない）
- 部署や会議体の通称
- 「例のフォルダ」「いつもの締め」「あの画面」——**指示語でごまかされている固有名**

**中途採用の人は、前の職場で別の言葉を使っていました。** 新卒の人は、どれが一般用語でどれが社内用語かを見分けられません。
そして**その場の全員が当たり前に使っている言葉ほど、聞き返しにくくなります。**

### ② 社内システム名・ツール名

「◯◯システムに登録してください」。名前は書いてあります。**ですが何をするシステムかは書かれていません。**

名前が付いていると説明した気になりますが、**読む人にとっては未知の固有名詞が1つ増えただけ**です。

> 直し方：`◯◯（受注内容を登録するシステム）に登録してください`

### ③ ★登場する人・組織・取引先の「関係性」

**用語の点検とは別の観点です。ここが抜けている資料が非常に多い。**

社名や部署名は書かれている。読む人もその名前は知っている。
**それでも「何をする相手なのか」が定義されていないと、資料は使えません。**

実際に起きること：

> 1つのシステムに2社が関わっている。片方は日々の**保守**、もう片方は**開発元**。
> ところが資料には「A社：システム保守」「B社：◯◯の開発元」としか書かれていない。
> **画面が想定どおりに動かないとき、保守の相手に仕様の変更を頼んでしまう。**
> 名前は知っているのに、**どこまでがその相手の契約範囲かが見えていない**から起きる。

部署間でも同じことが起きます。「◯◯部へ連絡」とだけ書いてあり、**その部署に何を頼めるのかが書かれていない。**

見るところ：

- その会社・部署は、**何を担当している相手か**
- 複数の相手が出るとき、**どこからどこまでが誰の責任か**
- 問題が起きたとき、**どの種類の問題を、どこへ持っていくのか**

**「名前を知っている」と「関係が分かっている」は別です。**

## 説明が要らないもの

読者を固定したうえで、**その読者が日常的に使う語**は説明しません。

- 事業者向けの記事での「見積」「請求書」「棚卸し」
- 開発者向けの記事での「Git」「CLI」「JSON」
- 誰にとっても一般的な「Excel」「メール」「フォルダ」

**説明を足しすぎると、逆に読みにくくなります。** 説明の数ではなく、**読者が止まる箇所を減らすこと**が目的です。

## 判定に迷ったときの問い

> **その読者が、その語を業務で口に出したことがあるか。**

あるなら説明不要。無いなら説明が要ります。
